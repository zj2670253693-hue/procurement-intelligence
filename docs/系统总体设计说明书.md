# 面向行业数据的智能实体挖掘与关系建模系统总体设计说明书

版本 1.0　日期 2026年10月16日

## 1 文档目的与系统边界

本系统面向政府采购公告及其附件，完成标的信息提取、采购主体关系分析和可交互的处理平台。我们采用国产大模型生成候选结果，用原文证据、确定性规则和人工审核约束结果，再通过版本化存储支撑查询与导出。大模型输出不是自动成立的业务事实，页面可用也不等于满足官方准确率或查询基准。

本文供参赛团队开发、部署、联调和答辩使用，说明当前代码的模块、数据结构、处理流程、资源限制及验收方法。任务一负责形成可追溯的抽取结果；任务二负责在有证据的结果上建立关系与五类查询；任务三负责个人登录、上传、后台任务、独立数据集、检索与导出。三者共用解析与抽取算法，但不能相互覆盖冻结数据。

本版本不包含自建 GPU 推理集群，不部署 Neo4j，不宣称已经进行 LoRA 或 QLoRA 微调，也没有适配器权重或训练损失曲线。生产模型的准确名称以实际调用账本和供应商响应为准，不能由 API 别名推断固定权重版本。

## 2 需求与业务口径

### 2.1 任务一实体提取

七个核心字段为产品服务名称、品目、品牌或产品供应商、规格型号、单价、数量、总价。需要结合 HTML 正文和附件，区分实际中标标的、采购需求、预算、入围意向及无法明确对应的信息。供应商、品牌和制造商是不同角色，不能把中标供应商直接填成品牌。

基础展示按采购包归口组织已经公示的标的信息，附件保留逐项明细和来源。附件中的需求清单不是实际中标清单；废标、未中标及仅入围资料不自动进入基础评分。基础层、附件明细层和标准三表是不同投影，行数不能直接相加，也不能把全部附件候选当成有效成交。

未知值在标准输出中留空，不填 0，不复制“详见附件”充当品牌或型号。只有附件实际存在、可读且能唯一对应时才从附件补充；附件不存在属于来源状态，不是品牌字段内容。原始响应和分类备注保留，便于复核。

### 2.2 金额和数量

项目归口以公告明确的项目或采购包成交金额为依据，产品归口以对应标的的金额为依据。项目总额不能无条件复制到每个产品或每家供应商；代理费、预算、最高限价和候选报价不能当成成交金额。未知包与供应商之间不按排列顺序配对。

只有明确字段和强逻辑关系才能支持计算。当前基础输出采用保守策略，优先保留明确公示且唯一归属的金额；没有相应信息时留空。禁止用包总价减去已知产品金额推算其他产品，也禁止用预算乘折扣率得到实际成交总价。原文数字和币种单位应保留，标准表按要求换算万元并保留原精度。特殊数量单位可以保留原格式，数值筛选必须区分数量和单位。

### 2.3 任务二查询

任务二实现以下五类分析，每类查询同时提供数据表、关系图和原文证据入口。

| 查询类型 | 输入主体 | 结果及约束 |
| --- | --- | --- |
| 合作供应商与产品供应商 | 采购人 | 区分中标供应商、明确产品供应商和纯品牌，不把品牌反推成制造商 |
| 高频竞标与组合 | 采购人 | 展示已公示竞标主体、频次和已知共现组合，部分名单不宣称完整 |
| 共同竞标主体 | 中标供应商 | 展示同项目或同包参与者；未知结果不当作未中标 |
| 共同采购人 | 多个中标供应商 | 取明确合作采购人的交集，金额只归属于自己的成交记录 |
| 共同竞标项目及结果 | 多个中标供应商 | 展示共同参与项目及已知结果，保留未知状态和项目与包的区别 |

官方要求查询结果与基准一致，不能以页面数量证明实现得分。我们将功能联通、原文支持、官方基准一致性分别验证；当前内部测试不是官方评分结果。

### 2.4 任务三平台

用户通过 HTTPS 登录，上传单篇或批量公告及对应附件。平台支持分片、续传、任务进度、取消、明确重试、部分成功、七字段筛选、关系查询和标准三表下载。上传默认只解析，只有服务器策略、个人权限和有限预算同时满足时，才允许显式创建收费抽取任务。

## 3 总体架构

浏览器通过 Nginx 访问 Vue 前端和 FastAPI。API 处理登录、上传、只读查询及任务控制，耗时解析和模型请求由独立串行 worker 执行。MySQL 同时保存正式数据、关系版本和私人任务状态，但使用不同数据层或数据库隔离。

浏览器 → Nginx HTTPS → Vue 页面与 FastAPI → MySQL 和共享运行目录。

上传任务 → 分片与输入校验 → 后台队列 → 文件解析和 OCR → 有界模型抽取 → 独立实体保存 → 原文验证的关系构建 → 检索与导出。

正式数据的读取不触发重新抽取。任务二可以完全利用已有候选缓存离线重建，不需要重新调用大模型。私人上传的关系构建同样是离线验证步骤，但上游实体抽取可能产生另行授权的模型费用，两者必须分开记录。

| 层次 | 技术或模块 | 主要责任 |
| --- | --- | --- |
| 前端 | Vue 3 Vue Router Element Plus | 数据集选择、表格、图谱、上传和状态反馈 |
| 接入层 | Nginx | HTTPS 终止、静态文件、API 反向代理、证书验证路径 |
| API | FastAPI | 参数约束、会话和所有权校验、分页、查询与下载 |
| 实体算法 | task1_entity_extraction | HTML 与附件解析、OCR、Prompt、后处理和七字段结果 |
| 关系算法 | task2_relationship_analysis | 身份、采购包、角色、名单、金额和证据验证 |
| 关系查询 | task2_query_service | 不可变版本导入、五类查询和图数据投影 |
| 任务平台 | task3_platform | 分片、队列、租约、用量账本、独立批次和产物 |
| 持久层 | MySQL 8 和共享文件目录 | 业务记录、检查点、版本清单、原始文件和导出文件 |

## 4 数据与存储设计

### 4.1 正式实体与原文

正式库保留 announcements、extracted_entities、extracted_entity_details、project_relations、bidders 五张既有表。公告以原始 HTML 文件前缀关联；附件以同前缀 ZIP 对应。附件展示必须验证文件实际存在，不能仅凭抽取结果中的文件名生成一个必然可下载的链接。

当前冻结数据为 1038 篇公告、6784 条基础记录和 14110 条按既有规则保存的附件明细。project_relations 和 bidders 是历史关系候选来源，不作为新关系层已经证明的事实。bidders 的历史布尔中标标记不能替代新层的 won、lost、unknown 语义。

标准三表是总表、标的表、投标人表。当前冻结投影对应 1470、6776、6172 行，与原始层不同是分类、归口和汇总方式不同，不能以此判断记录丢失。多包 UUID 依据项目和标段映射编号，不分包的记录不强行增加后缀；三表使用同一映射结果关联。

### 4.2 版本化关系层

关系层增加 t2_datasets、t2_active、t2_facts、t2_evidence 四张独立表。一个数据集版本绑定输入哈希、实现指纹、规则和序列化版本。事实、候选、证据和问题记录均带 dataset_id，不允许跨版本引用。

| 数据对象 | 关键内容 | 使用限制 |
| --- | --- | --- |
| Source | 公告 ID、HTML 哈希、编码、读取状态 | 不能用相同标题代替同一来源 |
| Candidate | 原始值、文件哈希、JSON 路径、生产者 | 模型候选不是已验证事实 |
| Fact | 类型、自然键、业务字段、状态、聚合资格 | 只有符合状态和口径的事实可查询或聚合 |
| Evidence | 原文片段、表格行列、物理单元格、字符位置 | 可回到对应来源，不以新生成文本冒充原文 |
| Issue | 原因码、公告、候选与事实引用、备注 | 记录冲突、未知、部分名单和意向排除原因 |

事实类型包括组织、竞标主体、项目、采购包事件、名单、参与、中标、供应关系和金额。validation_status 区分已验证、未解决、冲突和拒绝；identity_status 与 aggregation_eligibility 单独保存。名字相同并不自动证明同一法人，项目编号、轮次和包身份不足时，交易次数或金额可以为空。

导入先校验文件哈希，再在事务内写入新版本，完成后才可读取。重复导入必须校验已存记录的完整规范化哈希，不只比对行数。旧版本不覆盖，活动指针切换使用比较后交换；服务也可以通过保护的版本标记固定展示版本。

### 4.3 私人任务层

任务三有 13 张 t3_ 表，覆盖用户、会话、任务、数据集、上传文件、分片、公告、基础实体、明细、检查点、模型尝试、产物和运行状态。其关系查询依赖独立的 t2_ 四表，正式库与私人任务库不互相覆盖。

每个上传数据集有独立 upload_dataset_id，并关联 owner_id 和 task_id。标的数值投影使用 DECIMAL(65,30)，同时保留原始文本和单位。金额或数量未知时保持 NULL，不把解析失败转成 0。文件放在 release 以外的 shared runtime，代码和冻结展示资源不由服务账号改写。

## 5 任务一处理设计

### 5.1 输入解析

HTML 解析提取标题、正文与表格。附件解析覆盖 PDF、Word、Excel 等已有支持格式，保留成功文件、失败文件和状态。扫描 PDF 仅在文字层缺失或过少时触发 OCR，避免每页都识别。

长 PDF 采用前部、均匀中部及尾部抽页；报价、明细、中标等高价值文件提高页数上限。默认普通 PDF 文本页上限 20，高价值文件 60，OCR 每份 PDF 最多 5 页。抽页提高资源可控性，不等于已读完整 PDF；未解析页面和失败文件应保留提示，不能宣称附件百分之百覆盖。

OCR 引擎按需加载并加锁复用，避免重复加载模型占用内存。针对 PDF 双层字形重复采用局部阈值判断，不直接删除所有连续重复汉字，以免破坏正常叠词。OCR 误识别仍需来源核验，不能把识别成功当成事实正确。

### 5.2 候选提取与规则

Prompt 明确七字段、采购包粒度、实际成交和需求预算的区别，并要求未知不强填。超长内容分块处理，基础层与明细层分别保存。后处理约束引用词、服务描述、品目、规格、数值和完全重复记录，但不进行无证据的公司别名合并或金额分配。

人工审核采用初审、复核、仲裁及独立金标流程。离线评测固定候选、金标与映射规则，分别统计字段和标的级结果；不能为了提升指标修改金标。40 条人工金标不是 1038 篇的官方全量准确率证明。

### 5.3 输出投影

原始 JSON 用于复现和追溯，基础表用于检索，附件明细用于高级展示，标准三表用于比赛交付。三表导出需要保存后重新读取、核对表头、数量、UUID 关联和金额精度。正式下载校验冻结工作簿 SHA，不在下载请求中重新抽取或收费。

## 6 任务二关系与查询设计

### 6.1 从候选到事实

离线构建按公告逐篇读取 HTML，建立可定位的标题、段落和物理表格索引，再依次验证身份、关系、名单和金额。每一阶段保存未解决问题。畸形表格、跨度歧义、供应商与包映射不清等情况不按顺序猜测。

联合体作为一个竞标主体，成员关系单独表示；不能把全包金额分别分配给每个成员。品牌文本不是制造商组织，只在原文明确制造商或产品供应商角色时建立相应关系。中标供应商和投标人角色也分别验证，只有中标结果不能证明完整投标名单。

仅框架入围、采购意向、征集结果和协议折扣且未公示具体成交细节的来源，不产生普通成交、交易金额或共同竞标事实，原文和候选仍保留为展示及排除证据。第二阶段实际订单不因含“框架协议”字样就被一并排除；标题、正文否认语句及历史阶段需要结合判断。歧义和复杂混合阶段仍应保守复核。

### 6.2 聚合口径

announcement_count 是原文公告记录数；transaction_count 是身份和范围满足严格条件后的交易次数，两者不能互换。金额仅聚合已验证、币种明确、归属明确且无覆盖冲突的成交总额或产品金额；项目总额、包金额、分项金额重叠时不得相加。

本系统使用精确来源名称查询，未宣称完成全国法人实体消歧。因身份或轮次信息不足而不具备聚合资格时，显示未知或不适用，而不是 0。部分披露的竞标组合只表示已知共现，不证明完整名单，也不作为围标结论。

### 6.3 图表一致性

查询响应包含同一 dataset_id 下的表格、record_ids、evidence_ids 和图数据。图仅使用已验证事实生成边，不自动连接所有同现组织。图展示有节点和边的数量上限，截断必须明确标记。

前端按真实 node.id 识别节点，不能按显示名称合并两个不同项目的“合同包1”，也不能合并同名未消歧组织。仅重复出现的同一 ID 可以合并证据。边保留真实 edge.id，不把不同事实压成一条边，避免误连项目与供应商。数据集切换后丢弃迟到响应，图、表和证据不能展示不同版本。

## 7 任务三平台设计

### 7.1 登录与所有权

平台密码采用 scrypt 加盐哈希，数据库不保存可逆密码。会话保存 token 哈希，浏览器 Cookie 设置 Secure、HttpOnly 和 SameSite。修改请求核对同源及 CSRF，读取会话与修改业务分别处理。登录有单进程并发和速率限制。

任务、原文、分片、取消、重试、数据集和产物访问都校验个人 owner。匿名共享上传当前关闭。正式冻结数据提供只读展示，不能借官方数据集名称越过私人所有权。浏览器展示原文使用文本而不是执行 HTML，下载使用 attachment 与 nosniff，拒绝路径逃逸和链接路径。

### 7.2 上传与后台任务

分片按预声明字节数和 SHA 校验；相同分片重复提交幂等，已完成部分可以续传。服务器检查公告与附件配对、文件大小、压缩成员、解压总量、压缩比和磁盘预留。输入校验通过后才进入后台队列。

worker 串行领取任务，使用共享锁、租约、心跳和 epoch 防止重复处理及过期 worker 写入。每篇公告保存输入、处理指纹和检查点；重试是用户明确动作，不能在模型用量不确定时自动重发。取消请求在检查点生效，保留已有来源和诊断。

成功、部分成功、失败和取消是不同状态。损坏附件不能使整批成功结果消失；反过来，返回空 JSON 也不能自动证明原文没有标的。当前已存在表格标的覆盖检查，但对复杂非表格表述的空结果检测仍有局限，需要进一步扩展来源反例，不能宣称零漏抽。

### 7.3 模型调用与预算

收费抽取需要服务器开关、已登记模型策略、获授权 owner、明确模式及有限请求和 token 预算。API key 已配置不等于获得费用授权。服务端逐次记录 reserve、sent、response 和不确定状态，SDK 自动重试关闭。

预留上界与供应商实际报告用量分开保存；实际用量未知保持空值。当前预算以任务为单位约束，并非账户跨任务的永久累计消费上限。计数器代码哈希和批准标志只能证明配置身份，不能单独证明未来所有输入的 token 上界；验证材料需保留且更换模型后重新检查。

## 8 接口与前端交互

以下为主要接口族，完整参数以当前 FastAPI OpenAPI 与代码模型为准。接口分页、长度、枚举、范围和版本均由后端校验；前端校验只是交互辅助。

| 接口族 | 方法及路径 | 责任 |
| --- | --- | --- |
| 健康 | GET /api/health | 数据库连接和正式三类记录数量 |
| 正式标准导出 | GET /api/task1/export/standard | 校验后的冻结三表下载 |
| 关系概况 | GET /api/task2/summary | 固定关系版本和覆盖说明 |
| 组织选择 | GET /api/task2/organizations | 精确来源名称选项和角色过滤 |
| 关系查询 | POST /api/task2/query | 五查询、分页和同版本子图 |
| 原文证据 | GET /api/task2/evidence/{id} | 版本固定的原文位置和片段 |
| 个人会话 | /api/platform/auth | 登录、会话刷新和退出 |
| 上传与任务 | /api/platform/uploads 和 tasks | 分片、续传、完成、状态、取消和重试 |
| 个人数据集 | /api/platform/datasets/{id} | 实体、统计、原文、附件、产物和独立关系查询 |

用户从数据集选择器区分官方数据与私人批次。上传页面持续显示阶段、部分失败和预算错误；实体页面支持七字段组合条件、未知值、金额范围和明确数量单位；关系页面给出表格、图、证据及统计口径。界面不把填充率命名为准确率，不把公开错误中的服务器路径或源文本直接回显。

## 9 轻量服务器部署与资源限制

目标环境为 Ubuntu 24.04、2 vCPU、4GB 内存，MySQL、Nginx、单 API worker 和单后台处理 worker，不常驻 GPU 模型。GPU 可用于另行部署的模型训练或推理，不是当前轻量主机运行查询系统的必要条件。

| 资源项 | 当前设计或默认值 | 说明 |
| --- | --- | --- |
| API cgroup 内存上限 | 768 MiB | 必须包含整个服务进程组 |
| 后台 worker 内存上限 | 1024 MiB | 包括解析和导出子进程，禁止只测主进程 RSS |
| 活跃任务和模型并发 | 各 1 | 避免 2 核 4GB 同时启动多个 OCR 或模型任务 |
| 队列长度 | 10 | 超限明确拒绝，不无限积压 |
| 分片上限 | 16 MiB | 单请求另受服务端限制 |
| 单任务和全局运行盘配额 | 12 GiB 和 16 GiB | 另保留 4 GiB 空闲磁盘 |
| 文件解析超时 | 180 秒 | 后台任务总时限默认 6 小时 |

Limits 中的数值可由明确服务端配置调整，网页用户不能提高。历史命令行的 PROCESS_MAX_WORKERS 默认 2 与任务三串行 worker 不同，不能把两套入口同时运行造成实际超额并发。运维需同时关注 MySQL、系统余量、worker 子进程、swap 和 OOM。

release 保存只读代码和冻结资源，shared 保存虚拟环境、原文和私人运行目录。环境文件、API key、会话、数据库备份、金标和原始比赛附件不提交公共 GitHub。发布包只带允许的代码及构建前端，比赛数据单独授权传输和哈希核验。

HTTPS 证书与自动续期属于运行依赖。采用短期 IP 证书时，必须定期检查实际有效期、续期服务日志和公网信任链，不能以 timer active 代替将来续期成功。HTTP 入口应统一跳转 HTTPS，同时保留 ACME 验证路径；私人密码不能在旧 HTTP 页面提交。

## 11 发布与回滚

发布采用新目录、新版本、精确清单和哈希固定计划。先验证输入与旧数据指纹，再准备文件和追加不可变关系版本；不在服务器上直接覆盖运行中的算法文件。重复导入核验存储内容，禁止用清库重跑代替修复。

最终切换由管理员执行，操作者核对主机、旧与新 manifest、配置文件哈希和无活动任务。切换前保留环境、服务 unit、Nginx、旧 release、旧原文及数据库。任务二的新版本通过新 release 的版本标记被选中，旧事实与旧版本仍保留。

切换后检查本机和可信公网 HTTPS，验证任务一计数和冻结工作簿、任务二版本及五查询、任务三会话与批次，并复核旧表指纹及模型尝试数。失败时按实际修改恢复配置与服务，明确区分完全回滚、仅 HTTP 配置恢复和需人工处理，不能删除失败目录或原数据冒充恢复成功。

## 12 已知限制与维护重点

本系统以有证据、可复现为目标，不承诺对所有公告零错误。OCR 仍可能单字识别错误，长 PDF 只处理受限页；复杂非表格标的的空结果检测和模型空值规范化仍需增加反例。去重必须关注来源角色和页码，不能仅以七字段相同就否认不同来源的有效信息。

框架入围识别采用明确来源语义约束，复杂多阶段混合公告仍需复核。严格身份或采购轮次不足时，跨公告交易统计保持未知；若官方基准要求更充分的覆盖，应补充身份和范围证据并重新对照，不能通过放宽合并或强填金额凑结果。

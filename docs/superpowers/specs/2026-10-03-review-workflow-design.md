# 任务一人工审核工作流设计

## 1. 目标

在现有招采标讯平台中增加数据库驱动的人工审核工作流，支持两名队员依次完成初审和复核，由负责人处理分歧并生成最终标准答案。

成功标准：

- 初审员能够核对40篇公告的标的物完整性和七个核心字段。
- 复核员能够对照原文独立复核初审结果，并明确记录同意或异议。
- 仲裁员只处理有分歧的字段和标的物。
- 模型原始提取结果始终保留，不被人工审核覆盖。
- 最终结果能够导出为现有评测程序可读取的Excel或JSON。
- 所有提交记录审核人、提交时间和版本，避免并发覆盖。

## 2. 范围

本期包括：

- 审核批次、公告审核任务和标的物审核明细的数据表。
- 初审、复核、仲裁三个前端页面。
- 审核进度、任务详情、阶段提交、退回和最终导出接口。
- 审核状态流转、阶段锁定、争议识别和并发版本校验。
- 以审核人姓名记录操作者。

本期不包括：

- 完整的网页账号、登录和角色权限系统。
- 自动修改任务一模型或提示词。
- 用审核结果直接覆盖 `extracted_entities`。
- 多批次之间的复杂权限隔离。

服务器对外访问时可由Nginx统一访问密码保护网站，但不属于本审核模块的业务权限设计。

## 3. 角色

### 3.1 初审员

- 查看公告HTML、附件文本和模型提取结果。
- 检查标的物是否遗漏、重复或错误生成。
- 核对产品服务名称、品目、品牌、规格型号、单价、数量和总价。
- 标记正确、修改、删除、新增或无标的物。
- 对修改、删除和新增提供原文依据。

### 3.2 复核员

- 查看模型原值、初审值、公告原文和附件。
- 独立判断初审结果是否正确。
- 对每条记录选择同意或不同意。
- 不同意时填写建议值、问题字段和原文依据。

### 3.3 仲裁员

- 查看只包含分歧项的待仲裁列表。
- 对比模型值、初审值和复核值。
- 选择初审值、复核值或录入新的最终值。
- 可将整篇任务退回初审或复核。
- 完成仲裁并锁定最终标准答案。

## 4. 数据模型

### 4.1 `review_batches`

表示一次人工审核批次。

建议字段：

- `id`：主键。
- `name`：批次名称。
- `description`：说明。
- `status`：`draft`、`active`、`completed`。
- `created_by`、`created_at`、`completed_at`。

### 4.2 `review_cases`

一篇公告对应一个审核任务。

建议字段：

- `id`、`batch_id`、`announcement_id`。
- `status`：`pending_initial`、`pending_review`、`pending_arbitration`、`completed`。
- `initial_reviewer`、`review_reviewer`、`arbitrator`。
- `initial_submitted_at`、`review_submitted_at`、`arbitrated_at`。
- `version`：乐观锁版本号。
- `returned_stage`、`return_reason`。
- 唯一约束：`batch_id + announcement_id`。

### 4.3 `review_items`

保存每条标的物在各阶段的数据快照。

建议字段：

- `id`、`case_id`、`source_entity_id`、`item_order`。
- `model_data`：模型七字段JSON快照。
- `initial_data`、`initial_verdict`、`initial_evidence`、`initial_note`。
- `review_data`、`review_verdict`、`review_evidence`、`review_note`。
- `final_data`、`final_verdict`、`arbitration_note`。
- `is_added`、`is_deleted`、`has_dispute`。
- `created_at`、`updated_at`。

新增的漏检标的物使用 `source_entity_id = NULL` 和 `is_added = 1`。删除仅标记状态，不物理删除审核明细。

模型七字段使用JSON快照，保证后续重新提取或重新入库不会改变正在进行的人工验证集。

## 5. 状态流转

```text
pending_initial
    -> 初审提交
pending_review
    -> 复核无分歧
completed

pending_review
    -> 复核存在分歧
pending_arbitration
    -> 仲裁完成
completed
```

规则：

- 只有处于当前阶段的任务允许提交该阶段结果。
- 初审提交后，初审数据锁定；复核员只能写复核数据。
- 复核提交时比较初审和复核结果，自动设置 `has_dispute`。
- 没有分歧的任务自动生成最终数据并完成。
- 有分歧的任务只有仲裁员提交后才能完成。
- 仲裁员退回任务时必须填写原因，并清除被退回阶段之后的提交状态。
- 每次提交携带当前 `version`；数据库版本不一致时返回409，要求刷新后重试。

## 6. 页面设计

### 6.1 审核进度总览

显示批次名称、公告总数以及待初审、待复核、待仲裁和已完成数量。提供进入三个工作台的入口。

### 6.2 初审工作台

- 左侧：40篇公告任务列表、状态、实体数量、筛选和进度。
- 中间：公告原文与附件页签，附件按文件名展开。
- 右侧：七字段可编辑标的物列表。
- 操作：正确、修改、删除、新增标的物、保存草稿、提交初审。
- 修改、删除和新增时依据为必填项。

### 6.3 复核工作台

- 左侧：待复核公告列表和进度。
- 中间：公告原文与附件。
- 右侧：模型原值与初审值并排展示，变化字段高亮。
- 操作：同意初审、不同意并录入建议值、保存草稿、提交复核。
- 不同意时建议值和依据为必填项。

### 6.4 仲裁工作台

- 默认只展示 `has_dispute = 1` 的标的物或字段。
- 并排展示模型值、初审值和复核值。
- 每个争议字段可选择初审值、复核值或填写新值。
- 支持退回初审、退回复核和提交最终仲裁。
- 提交后任务锁定为已完成。

## 7. API设计

建议路由前缀为 `/api/reviews`：

- `GET /summary`：批次进度汇总。
- `GET /batches`：批次列表。
- `POST /batches`：从指定公告ID创建审核批次和模型快照。
- `GET /cases`：按批次、状态、公告ID分页查询任务。
- `GET /cases/{case_id}`：公告、附件、模型值及各阶段审核详情。
- `PUT /cases/{case_id}/initial`：保存初审草稿。
- `POST /cases/{case_id}/initial/submit`：提交初审。
- `PUT /cases/{case_id}/review`：保存复核草稿。
- `POST /cases/{case_id}/review/submit`：提交复核并计算分歧。
- `PUT /cases/{case_id}/arbitration`：保存仲裁草稿。
- `POST /cases/{case_id}/arbitration/submit`：提交最终结果。
- `POST /cases/{case_id}/return`：退回指定阶段。
- `GET /batches/{batch_id}/export.xlsx`：导出评测Excel。
- `GET /batches/{batch_id}/export.json`：导出标准答案JSON。

写接口需要审核人姓名、当前版本号和本阶段完整明细。后端负责验证必填依据、状态合法性和版本一致性，不能只依赖前端校验。

## 8. 最终答案与评测导出

最终数据按以下规则生成：

- 有仲裁结果时使用 `final_data`。
- 复核无异议时使用复核确认后的初审数据。
- 标记删除的实体不导出。
- 新增实体正常导出。
- 输出工作表保持现有评测器要求的字段名称和 `核验结论` 列。
- 只有批次全部完成后允许正式导出；未完成时返回明确错误。

价格字段遵循比赛口径：只采用明确成交金额或明确标的物报价；预算、最高限价、市场指导价折扣不能推算为成交金额。

## 9. 错误处理

- 非当前阶段提交返回409。
- 版本冲突返回409并提示刷新。
- 修改、删除、新增或异议缺少依据时返回422。
- 公告源文件缺失时仍展示数据库中的 `raw_text`，并明确提示附件不可用。
- 附件解析失败不阻断审核，但记录提示信息。
- 草稿保存失败时保留前端未提交内容并允许重试。

## 10. 测试与验收

后端测试：

- 建表和批次初始化。
- 四种状态的合法与非法流转。
- 初审、复核、仲裁字段及依据校验。
- 自动争议识别。
- 新增、删除和无标的物场景。
- 乐观锁冲突。
- 最终Excel和JSON导出。

前端测试：

- 三个页面能加载对应状态任务。
- 七字段编辑、对比高亮和争议筛选正确。
- 必填依据校验。
- 保存草稿、提交、退回和刷新冲突提示。
- 生产构建通过。

端到端验收：

- 使用一篇包含修改、删除、新增和价格争议的样例公告走完全部流程。
- 确认模型原表未变化。
- 确认最终导出能够被 `run_evaluation.py` 读取并生成评测报告。

# 任务一离线人工金标评测设计

## 1. 目标

把人工完成初审、复核与近似仲裁后的40篇公告 JSON 作为任务一当前可信金标，替换原先由模型结果反向生成、因而得到虚假100%分数的验证方式。

成功标准：

- 评测入口能够直接读取审核系统导出的 JSON，不要求先人工转换成 Excel。
- 严格校验40个不重复公告及七个核心字段，输入异常时明确失败。
- 计算准确率、精确率、召回率、F1和比赛综合得分。
- 除汇总指标外，输出可定位到公告、实体和字段的错误明细。
- 人工审核 JSON、审核人姓名和错误明细均不进入 Git 仓库。
- 现有 Excel 验证集入口保持兼容。

当前人工金标试算基线为40篇公告、273条实体：准确率67.11%、精确率71.85%、召回率91.05%、F1 80.32%、比赛综合得分75.71%。该试算仅用于确认方案可行，正式数字以新评测入口生成的报告为准。

## 2. 范围

本期包括：

- 审核 JSON 加载、结构校验和金标实体生成。
- 现有 `run_evaluation.py` 对 `.json` 与 `.xlsx` 的自动识别。
- 复用现有实体对齐与字段匹配口径计算指标。
- 生成正式人工金标汇总报告和逐字段错误 CSV。
- 为 JSON 加载、删除/新增实体、空值、实体乱序和错误分类增加自动化测试。
- 补充离线评测命令说明与数据保密说明。

本期不包括：

- 把 JSON 回写到服务器审核数据库。
- 自动修改 Prompt、OCR或抽取规则。
- 重新调用大模型跑全量1038篇公告。
- 把人工金标或错误明细提交到 GitHub。
- 修改人工审核页面和状态流转。

评测完成后，下一阶段再根据错误清单按影响排序修改抽取逻辑，并用同一份金标做前后对比。

## 3. 方案选择

采用“扩展现有评测器直接读取审核 JSON”的方案。

没有采用“JSON 转 Excel 后再评测”，因为中间转换增加了操作步骤和字段映射风险。没有采用一次性脚本，因为比赛期间还会产生新的复核或仲裁版本，需要稳定、可重复的命令。

## 4. 输入与金标生成

### 4.1 命令行输入

`run_evaluation.py` 接受一个金标文件路径：

- 后缀为 `.xlsx` 时，继续调用现有 Excel 加载逻辑。
- 后缀为 `.json` 时，调用新的审核 JSON 加载逻辑。
- 其他后缀直接报错，不根据内容猜测格式。

人工金标路径由使用者在命令行传入，不复制到仓库内固定目录，也不写入配置文件。

### 4.2 JSON结构

审核 JSON 顶层必须包含 `cases` 数组。每个 case 必须包含：

- `announcement_id`：非空字符串，在文件内唯一。
- `items`：数组。

每个 item 使用 `data` 中的七个字段：

- `product_name`
- `category`
- `brand`
- `spec_model`
- `unit_price`
- `quantity`
- `total_price`

缺少某个字段时按空字符串处理，但缺少 `data`、`announcement_id` 或数组结构错误时拒绝评测，避免悄悄生成错误金标。

### 4.3 实体纳入规则

- `is_deleted = true` 的实体不进入金标。
- `initial_verdict` 为“删除”“删除该行”或 `delete` 的实体不进入金标。
- `is_added = true` 的实体只要七字段至少一项非空，就正常进入金标。
- 七字段全部为空的实体不进入金标。
- 保留真实空字符串，不把空值自动改写为“未公示”“无”或其他占位符。
- 如果七字段仍包含精确占位值“未公示”，加载器给出明确校验错误，要求先确认并清洗，而不是静默改变人工答案。

当前版本要求输入恰好包含40个不重复公告。以后需要评测其他规模的验证集时，可以通过显式命令行参数调整预期数量，默认值仍为40。

## 5. 指标与实体对齐

指标继续使用现有 `Evaluator`：

- TP：预测非空、金标非空且字段匹配。
- FP：预测非空但未匹配，或金标对应字段为空。
- FN：金标非空但没有被正确预测。
- 准确率：`TP / (TP + FP + FN)`。
- 精确率：`TP / (TP + FP)`。
- 召回率：`TP / (TP + FN)`。
- F1：精确率和召回率的调和平均。
- 比赛综合得分：准确率×0.4 + 精确率×0.3 + 召回率×0.3。

实体仍使用现有相似度对齐逻辑，避免输出顺序不同导致整篇错配。正式错误清单必须复用同一套对齐和字段匹配方法，不能出现“汇总指标判断正确、错误清单却判断错误”的双重口径。

## 6. 错误清单

新增独立的错误审计组件，输入预测结果、金标结果和 `Evaluator` 的匹配口径，输出每个错误字段一行。

CSV至少包含：

- `announcement_id`
- `prediction_entity_index`
- `gold_entity_index`
- `product_name_context`
- `field`
- `prediction_value`
- `gold_value`
- `error_type`

错误类型固定为：

- `wrong_value`：预测与金标均非空但不匹配。
- `false_positive`：预测非空、金标为空。
- `false_negative`：预测为空、金标非空。
- `extra_entity`：预测实体未与任何金标实体对齐。
- `missing_entity`：金标实体未与任何预测实体对齐。

多余或遗漏实体按其每个非空字段分别输出一行，使CSV错误数量能够与评测器的FP/FN数量核对一致。

## 7. 输出文件

正式运行写入 `task1_entity_extraction/output/`：

- `evaluation_report_human_gold.json`：汇总指标、字段指标、样本数、实体数、输入文件名和生成时间。
- `evaluation_errors_human_gold.csv`：逐字段错误明细，使用 UTF-8 with BOM，便于直接用 Excel 打开中文。

不覆盖旧的 `evaluation_report.json`，避免把旧100%报告误认为人工金标结果。输出中的输入文件只记录文件名，不写绝对路径或审核人信息。

## 8. 代码边界

- `run_evaluation.py`：命令行解析、按后缀选择加载器、调用评测和写出报告。
- `evaluation/ground_truth.py`：Excel与审核 JSON 金标加载和校验。
- `evaluation/audit.py`：复用实体对齐与字段匹配口径生成错误明细。
- `evaluation/metrics.py`：保留指标职责；只在需要公开稳定的对齐/匹配接口时做最小调整。
- `tests/test_ground_truth.py`：JSON加载与输入校验测试。
- `tests/test_evaluation_audit.py`：错误分类和统计一致性测试。
- `tests/test_run_evaluation.py`：命令行格式选择和输出文件测试。

各模块保持单一职责，不把 JSON 解析、指标计算和 CSV 写出继续堆入一个脚本。

## 9. 错误处理

以下情况以非零退出码失败，且不生成或覆盖正式报告：

- 文件不存在或后缀不支持。
- JSON不是合法UTF-8或不是合法JSON。
- `cases`、`items`、`data` 的结构错误。
- 公告ID为空或重复。
- 公告数与预期40不一致。
- 七字段包含未清洗的“未公示”占位值。
- 预测结果中同一公告ID重复。

某篇金标合法但在预测结果中缺失时不属于输入错误，按整篇漏报计入评测和错误清单。

## 10. 测试与验收

自动化测试覆盖：

- 40篇审核 JSON 正常加载。
- 删除实体被排除，新增实体被保留。
- 空字符串原样保留，全空实体被跳过。
- “未公示”占位值触发明确错误。
- 重复公告ID、数量错误、结构错误被拒绝。
- 实体顺序变化不影响对齐结果。
- 五种错误类型均能生成正确明细。
- 错误CSV中的FP/FN数量与汇总指标一致。
- 现有 Excel 加载方式继续可用。
- 正式输出不覆盖旧报告，且不泄露绝对路径或审核人信息。

真实数据验收：

1. 使用清洗后的40篇人工 JSON 运行命令。
2. 确认读取40篇、273条金标实体。
3. 确认正式指标与只读试算结果在相同口径下保持一致。
4. 抽查第9篇附件缺失案例，确认品牌采用同行供应商、其余未披露字段为空。
5. 打开错误CSV，确认中文正常并能按字段、错误类型和公告ID筛选。
6. 检查 Git 暂存内容，确认没有人工金标、审核人姓名、API Key或错误明细。

## 11. 数据与仓库安全

- 人工审核 JSON 只保存在用户指定的本地位置。
- 运行命令、日志和报告不输出审核人姓名。
- `.gitignore` 必须覆盖人工金标及生成的错误明细；如果现有规则不足，只补充最小必要规则。
- Git 提交只包含脱敏代码、测试构造数据和文档。
- 测试样例使用虚构公告ID、供应商和产品名称，不复制真实比赛数据。

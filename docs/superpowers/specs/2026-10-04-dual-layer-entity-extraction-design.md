# 任务一双层实体提取设计

## 1. 背景

任务一当前把公告正文和附件内容合并后一次性交给大模型，并将所有结果写入同一个 `entities` 列表。这种做法能够挖掘附件中的设备明细，但也混淆了两种不同粒度：

- 比赛基础结果需要按采购包汇总，用于七字段准确性评测；
- 高级展示需要保留附件中的产品、设备或服务明细，用于证明附件覆盖能力。

离线人工金标评测显示，粒度混淆会把一份包含大量设备的附件输出成几十条基础实体，而人工金标只保留采购包汇总，从而产生大量误报。当前 Prompt 对“品牌（产品供应商）”的解释也偏向产品品牌，而人工审核口径在采购包汇总层优先采用明确的中标或成交供应商。

## 2. 目标

系统同时提供两层结果：

1. **基础层**：每个采购包一条记录，继续使用现有 `entities` 字段、数据库表和接口，作为比赛基础准确性评测输入。
2. **明细层**：保存附件中逐项提取的设备或服务清单，使用新增的 `detail_entities` 字段、数据库表和接口，作为技术先进性和附件覆盖能力展示。

本设计还需要满足以下约束：

- 兼容现有前端和 API，不改变现有 `entities` 的七字段结构；
- 适配 2 vCPU、4 GB 内存的 Ubuntu 24.04 部署环境；
- 支持检查点和断点续跑，避免故障后重新调用全部模型接口；
- 不将私有金标、比赛原始数据、API Key、服务器密码或真实公告内容提交到 Git；
- 不使用预算、最高限价或折扣比例推算成交金额。

## 3. 非目标

- 本阶段不重做 OCR 引擎或附件解析器；
- 本阶段不改变任务二的关系建模语义；
- 本阶段不为所有历史附件立即重新调用大模型；
- 本阶段不将附件明细混入基础准确率指标；
- 本阶段不根据采购品目目录自行推断原文未出现的品目。

## 4. 数据模型

### 4.1 基础结果

现有 `ExtractionResult.entities` 保持不变。列表中每一项仍然只有官方要求的七个字段：

- `product_name`
- `category`
- `brand`
- `spec_model`
- `unit_price`
- `quantity`
- `total_price`

其语义调整为“采购包级基础结果”，每个采购包最多产生一条基础记录。

### 4.2 附件明细

`ExtractionResult` 新增：

```json
{
  "detail_entities": [
    {
      "package_name": "采购包名称或编号",
      "source_file": "来源附件文件名",
      "source_page": "来源页码或空字符串",
      "product_name": "产品服务名称",
      "category": "品目",
      "brand": "品牌或产品供应商",
      "spec_model": "规格型号",
      "unit_price": "单价",
      "quantity": "数量",
      "total_price": "总价"
    }
  ],
  "detail_status": "available"
}
```

新生成和对外返回的 `detail_status` 只允许以下值：

- `available`：存在可用附件，且成功得到明细；
- `missing`：公告引用附件，但数据集中没有对应文件；
- `unreadable`：附件存在，但解析器不能读取；
- `no_attachment`：公告本身没有附件；
- `extraction_failed`：附件已经解析，但明细提取失败。

读取旧结果时允许该字段暂时为 `null`，不得导致现有 JSON 无法导入。迁移程序必须结合公告附件元数据把 `null` 解析为上述五种状态之一，解析完成前不得把该记录写入正式数据库或通过 API 返回，避免把旧附件公告误标为 `no_attachment`。

## 5. 基础层提取

### 5.1 输入边界

基础层只接收：

- HTML 正文文本；
- HTML 正文表格；
- 附件存在性、解析状态和附件文件名等元数据。

基础层 Prompt 不接收附件全文或附件表格，避免附件中的几十条明细污染采购包级输出。

### 5.2 采购包粒度

- 有明确采购包时，每包输出一条基础记录；
- 未分包时，整篇公告输出一条基础记录；
- 同一采购包在正文段落和多个正文表格中重复出现时，只保留一条；
- 采购包标识用于内部对齐，不增加到官方七字段中；必要时包含在 `product_name` 的原文名称里。

### 5.3 七字段规则

#### 产品服务名称

- 优先采用正文明确给出的采购标的或采购包名称；
- 不用附件中的单个设备名称替换采购包名称；
- 保留能够区分采购包的原文编号或名称。

#### 品目

- 只提取正文明确出现的品目编码或类别；
- 同一包对应多个明确品目时，按原文顺序使用英文逗号连接；
- 原文没有品目时留空，不自行分类。

#### 品牌（产品供应商）

- 采购包级基础结果优先填写该包明确的中标或成交供应商；
- 不用附件中的某一个产品品牌代表整个采购包；
- 未明确对应供应商时留空，不跨采购包复制。

#### 规格型号、单价、数量

- 正文明确给出单一包级值时按原文提取；
- 正文只写“详见附件”且附件状态为 `missing` 或 `unreadable` 时写“附件缺失”；
- 正文只写“详见附件”且附件状态为 `available` 时留空，具体值进入明细层；
- “详见附件”“详见采购文件”“按招标要求提供”等引用性文字不能直接作为字段值。

#### 总价

- 优先采用明确的中标金额或成交金额；
- 只存在预算、最高限价、折扣率、下浮率或市场指导价比例时留空；
- 禁止用预算乘比例、单价乘数量等方式推算未公示成交金额；
- 保留原文金额单位。

### 5.4 确定性校验

模型输出后执行确定性校验：

- 删除引用性占位词；
- 按采购包稳定去重；
- 检查成交金额来源，拒绝把预算或限价写入总价；
- 根据附件状态处理“附件缺失”；
- 拒绝一个采购包输出多条互相冲突的基础记录，并记录诊断信息。

确定性校验只清理和约束模型结果，不凭空补造正文中不存在的信息。

## 6. 明细层提取

### 6.1 输入与分段

明细层只处理成功解析的附件内容：

- 优先发送结构化附件表格；
- 普通文本作为表格缺失时的补充；
- 长 PDF 按表格所在页以及首、中、尾代表页分段；
- 单次请求必须设置输入字符和输出 token 上限，避免长附件截断整批结果。

### 6.2 采购包归属

- 优先使用附件中的采购包标题、表头或章节信息；
- 无法识别采购包时使用空字符串，不猜测归属；
- 前端可把未识别归属的记录显示在“未分包明细”区域。

### 6.3 去重

同一公告、同一采购包内，七字段归一化后完全相同的明细只保留首次出现项。来源文件和页码不参与业务去重，但首个来源需要保留用于追溯。

### 6.4 复用现有结果

已有 `raw_results.json` 中的行级结果作为明细候选迁移，不立即重新调用所有附件：

- 迁移时保留七字段；
- 缺少可靠来源信息时，`source_file` 和 `source_page` 留空；
- 无法确定采购包时，`package_name` 留空；
- 迁移不会把旧明细继续保留在基础层。

后续只对附件解析逻辑、Prompt 或去重规则发生变化的公告增量重跑明细层。

## 7. 持久化与接口

### 7.1 数据库

现有 `extracted_entities` 表继续保存基础结果。新增 `extracted_entity_details` 表，至少包含：

- 主键 `id`；
- `announcement_id`；
- `package_name`；
- 七个实体字段；
- `source_file`；
- `source_page`；
- 创建时间；
- `announcement_id` 索引。

明细表按公告进行幂等替换：只有该公告的新明细已经完整验证后，才替换旧明细。

`announcements` 表新增 `detail_status VARCHAR(32) NULL` 和 `detail_error_message TEXT`。新处理记录写入上述五种正式状态；旧记录在迁移完成前允许为 `NULL`。数据库迁移必须可重复执行，不得删除现有基础结果。

### 7.2 API

保持现有接口语义：

- `GET /task1/entities/{announcement_id}`：只返回采购包级基础结果；
- 新增 `GET /task1/entities/{announcement_id}/details`：返回附件明细和 `detail_status`；
- 统计接口分别返回基础实体数和附件明细数；
- 搜索接口默认搜索基础结果，明细搜索作为显式参数或独立接口提供。

### 7.3 前端

- 公告详情页默认展示采购包级结果；
- 每个公告提供“附件明细”入口；
- 明细按采购包分组，并显示来源附件和页码；
- 缺失、不可读或提取失败必须显示不同状态，不能统一显示为空。

## 8. 流水线、资源与故障恢复

基础层和明细层拥有独立检查点，避免其中一层失败导致另一层重跑。

- 默认并发为 2；
- 每处理 10 条公告保存一次检查点；
- 已成功且输入指纹未变化的记录在断点续跑时跳过；
- 新输出先写临时文件并完成结构校验，再原子替换对应正式文件；
- 单条基础提取失败时保留上一版基础结果并记录失败原因；
- 明细提取失败只更新 `detail_status`，不得清空已经验证的基础结果；
- 全量运行前先执行 40 条人工金标小批次验证。

大模型计算发生在远端 API。本地 2 vCPU、4 GB 服务器主要承担文本解析、请求调度和数据存储；限制并发与分段上限后不需要 GPU。

## 9. 评测与测试

### 9.1 评测边界

- 离线人工金标评测只读取 `entities`；
- `detail_entities` 不参与基础准确率、精确率或召回率；
- 附件明细另行统计附件覆盖率、可追溯率和字段填充率；
- 当前离线基线为：准确率 67.11%、精确率 71.85%、召回率 91.05%、F1 80.32%、综合得分 75.71%。

### 9.2 自动化测试

需要覆盖：

- 基础 Prompt 不包含附件全文；
- 多采购包公告每包只生成一条基础记录；
- 大量附件明细不会增加基础实体数量；
- 中标供应商按采购包写入基础层品牌字段；
- “详见附件”按附件状态转换为空值或“附件缺失”；
- 预算和比例不能生成成交金额；
- 显式成交金额优先于预算与限价；
- 明细跨正文和多个附件稳定去重；
- 旧 JSON 能够向后兼容导入；
- 数据库迁移幂等；
- 新旧 API 均保持预期响应；
- 检查点续跑不会重复调用成功记录。

测试夹具必须使用虚构公告、供应商、金额和文件名，不纳入真实比赛数据。

### 9.3 第一轮验收门槛

- 40 条人工金标综合得分必须高于 75.71%；
- 精确率必须高于 71.85%，且不得通过删除所有预测来换取虚假提升；
- 基础层不得出现“详见附件”等引用性占位词；
- 现有附件详细清单不得因基础层改造而丢失；
- 新增测试、原有 pytest 和 `test_framework.py` 全部通过；
- 典型的“少量采购包、大量附件设备”场景必须验证基础与明细数量彼此独立。

## 10. 发布顺序

1. 增加数据模型、状态枚举和向后兼容读取；
2. 增加基础层输入隔离、Prompt 和确定性校验；
3. 增加明细数据模型、现有结果迁移和去重；
4. 增加数据库表、DAO 和 API；
5. 使用虚构数据完成自动化测试；
6. 仅重新提取 40 条人工金标的基础层；
7. 比较新旧评测报告并人工检查典型案例；
8. 达到验收门槛后，按检查点运行全部公告的基础层；
9. 根据附件覆盖需求增量重跑明细层；
10. 前端接入附件明细展开功能。

## 11. 失败与回滚

- 新字段和新表均为增量添加，旧代码可忽略；
- 正式切换前保留旧 `raw_results.json` 和数据库备份；
- 40 条评测未达到门槛时不进行全量基础层替换；
- 全量运行发生异常时从检查点恢复；
- 数据库导入失败时不提交该公告的新基础或明细事务；
- 回滚时恢复旧基础结果即可，明细表可以保留但不对外展示。

## 12. 安全与脱敏

- API Key 和数据库密码只通过环境变量或服务器私有 `.env` 提供；
- 私有金标和原始数据目录写入 `.gitignore`；
- 日志不得打印密钥、完整 Prompt 或包含敏感内容的附件全文；
- Git 提交前扫描常见密钥格式、服务器密码、真实公告 ID 和私有数据文件名；
- 文档、测试和示例只使用虚构内容。

## 13. 已排除方案

### 单次模型调用同时输出两层结果

调用次数较少，但长附件容易导致输出截断，模型也容易继续混淆采购包与设备行，不采用。

### 只用后处理把明细合并成采购包

无法可靠判断跨表格、跨附件和多采购包的归属，容易误合并真实标的物，不采用。

### 丢弃附件明细，只保留采购包

虽然能够减少基础误报，但会损失附件覆盖率和技术先进性展示，不采用。

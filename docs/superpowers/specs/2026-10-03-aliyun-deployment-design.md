# 阿里云轻量环境部署设计

## 1. 目标

将现有“面向行业数据的智能实体挖掘与关系建模”项目部署到比赛指定规格附近的阿里云环境，并形成可重复验证的生产部署基线。

目标服务器条件：

- Ubuntu 24.04
- 2 vCPU
- 4 GB 级内存（当前系统可见约 3.4 GiB）
- 约 49 GB 系统盘
- 公网 IP 提供 Web 访问

部署成功的判定标准：

1. 浏览器能够通过服务器公网 IP 打开前端。
2. `/api/health` 能够返回健康状态和数据库数据量。
3. MySQL 中包含当前 1038 篇公告和对应实体结果。
4. 服务器重启后 Nginx、MySQL 和后端服务能够自动恢复。
5. 空闲与典型查询状态下资源使用稳定；OCR 或提取任务不会因默认高并发耗尽 4 GB 内存。

## 2. 部署范围

首阶段部署以下内容：

- FastAPI 后端及任务一相关接口。
- Vue 前端的生产构建产物。
- MySQL 表结构。
- 当前已生成的 1038 篇公告、6856 条标的物结果及关系数据。
- Nginx 反向代理和 systemd 后端服务。
- 2 GB Swap，用于降低 OCR 峰值内存导致进程被杀的风险。

首阶段不上传约 3.5 GB 的原始附件包。原因是服务器带宽约 1 Mbps，直接上传耗时长，并且当前实体结果早于最新 OCR 修复。原始附件和最新版全量重跑作为部署后的独立阶段处理，不能使用会跳过已有成功记录的 `--resume`。

## 3. 方案选择

### 3.1 采用：原生轻量部署

采用 Nginx、systemd、Python 虚拟环境和 MySQL 的原生组合。

优点：

- 资源占用低，适合 2 核 4 GB。
- 服务状态和日志易于在答辩中展示。
- 不依赖额外容器运行时。
- 能直接体现与决赛 Ubuntu 24.04 环境的兼容性。

### 3.2 未采用：Docker Compose

Docker 有利于环境复制，但当前服务器没有安装 Docker；在 4 GB 内存下还会增加常驻资源和镜像空间。首阶段不引入。

### 3.3 未采用：普通用户临时进程

直接运行 Uvicorn 和静态文件服务器无需系统权限，但缺少开机自启、反向代理、稳定日志和进程恢复，不符合比赛演示与实际转化要求。

## 4. 运行架构

```text
公网用户
   |
   v
Nginx :80
   |-- /              -> Vue 静态文件
   `-- /api/*         -> 127.0.0.1:8000
                              |
                              v
                      FastAPI / Uvicorn
                              |
                              v
                    MySQL 127.0.0.1:3306
```

约束：

- 只向公网开放 SSH 和 HTTP。
- Uvicorn 只监听 `127.0.0.1:8000`。
- MySQL 只监听本机，不开放公网 3306。
- Uvicorn 使用 1 个进程，避免多进程重复加载 OCR 模型。
- 后端提取线程默认限制为 2。
- RapidOCR 保持单实例惰性加载，并串行执行推理。

## 5. 用户和目录

系统管理由 `admin` 账户负责；应用文件由普通用户 `zhoujin` 管理。不给 `zhoujin` 长期管理员权限。

建议目录：

```text
/srv/procurement-app/
├── backend/          Python 后端代码和虚拟环境
├── frontend/         Vue 生产构建文件
├── data/             小体积导入数据和结果文件
├── logs/             应用日志（由 journald 为主）
└── releases/         后续版本目录
```

系统文件：

```text
/etc/systemd/system/procurement-api.service
/etc/nginx/sites-available/procurement-app
/etc/nginx/sites-enabled/procurement-app
```

敏感配置放入服务器端环境文件，不写入 Git，也不输出到部署日志。当前已在聊天中出现的用户密码应在部署后立即更换。

## 6. 资源控制

### 6.1 后端

- Uvicorn workers：1。
- 实体提取线程：2。
- 附件覆盖分析线程：2。
- OCR 每个 PDF 最多处理 5 个弱文字页。
- OCR 推理串行。
- 文件上传采用分块写入，禁止一次性读入整个外层压缩包。

### 6.2 MySQL

- InnoDB Buffer Pool 目标 256 MB。
- 最大连接数控制在 30 左右。
- 禁止公网监听。
- 首阶段只保存结构化结果和必要公告文本，不保存附件二进制。

### 6.3 系统

- 增加 2 GB Swap。
- 保留至少 10 GB 磁盘余量。
- Nginx 设置合理的上传大小和请求超时，但首阶段不通过 Web 上传 3.5 GB 数据包。

## 7. 数据迁移

首阶段传输：

- 后端源代码，不包含缓存、Windows MySQL 数据目录和本地密钥。
- 前端生产构建产物。
- `raw_results.json`、CSV 结果和必要报告。
- 体积较小的 HTML 数据包，按需用于公告原文入库。

禁止传输：

- `.env` 中未审核的本地专用配置。
- 私钥、密码、缓存目录、`node_modules`。
- Windows 版 MySQL 二进制和 `mysql-data` 目录。

数据库在 Ubuntu 上新建，通过项目表结构和导入脚本生成，不能直接复制 Windows MySQL 数据目录。

## 8. 服务管理与日志

后端由 `procurement-api.service` 管理：

- 开机自启。
- 异常退出自动重启。
- 以 `zhoujin` 身份运行。
- 工作目录固定到后端目录。
- 从独立环境文件加载数据库和模型 API 配置。

日志通过以下方式检查：

```text
systemctl status procurement-api
journalctl -u procurement-api
nginx access/error log
MySQL error log
```

## 9. 验证方案

部署过程中按以下顺序验证：

1. 检查 Python 虚拟环境能够导入项目依赖。
2. 运行项目框架测试；记录因外部服务不可用而跳过的项目。
3. 验证 MySQL 表结构和导入行数。
4. 直接访问 `127.0.0.1:8000/api/health`。
5. 通过 Nginx 访问 `/api/health`。
6. 通过公网 IP 打开前端并查询实体。
7. 重启后端服务，确认自动恢复。
8. 在 2 核 4 GB 环境进行小样本提取，记录耗时、峰值内存和失败信息。

验收时必须区分：

- 附件解析覆盖报告已经在最新解析器上全量重跑。
- 当前实体结果仍早于最新 OCR 修复。
- `evaluation_report.json` 的旧 100% 结果不是人工核验后的真实准确率。

## 10. 回滚和故障处理

- 上传新版本前保留上一版本目录。
- Nginx 配置修改前先执行语法检查，只有检查通过才重载。
- systemd 服务启动失败时保留旧版本软链接或工作目录，恢复上一版本。
- MySQL 导入前建立数据库备份；导入脚本保持幂等。
- 不关闭当前可用的 SSH 管理会话，直到新服务验证完成。

## 11. 后续阶段

完成首阶段部署后再进行：

1. 使用最新 OCR 与附件解析逻辑重新提取全部 1038 篇公告。
2. 将新旧结果分版本保存，禁止覆盖唯一可用结果。
3. 完成 40 篇、273 行验证集的人工核验。
4. 重新计算真实准确率、精确率、召回率和综合得分。
5. 按官方计时口径在 2 核 4 GB 环境记录完整运行时间。
